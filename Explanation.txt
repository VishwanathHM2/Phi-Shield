1.	What it does and the problem it solves
This project is a PHI de-identification system for clinical text and PDF reports. It detects sensitive patient data such as:
•	NAME
•	DOCTOR
•	HOSPITAL
•	LOCATION
•	DATE
•	PHONE
•	EMAIL
•	ID
And then redacts it with placeholders like [NAME], [DATE], etc.
This is not a full web app backend with user auth or a database. It is a local ML/NLP pipeline that:
•	reads PDF clinical reports,
•	extracts text,
•	labels PHI using a BiLSTM + CRF model,
•	evaluates the model with entity-level F1,
•	redacts text through the model or regex fallback,
•	exposes a Streamlit UI for text/PDF input.
The project is explicitly built around a clinical NLP task. Evidence:
•	README.md states: “A production-ready AI system for detecting and anonymizing Protected Health Information (PHI) from clinical reports…”
•	run_pipeline.py orchestrates generation, training, evaluation, and UI launch.
•	utils/phi_extractor.py defines PHI types and regex extraction logic.

3.	Architecture and complete data/execution flow
High-level architecture:
•	Input: raw clinical text or PDF
•	Extraction: PDF parsing or OCR fallback
•	Annotation: regex-based PHI detection + BIO tagging
•	Dataset creation: CoNLL-style token/tag pairs
•	Training: BiLSTM + CRF on tokenized sentences
•	Evaluation: entity-level precision/recall/F1
•	Inference: predict tags, reconstruct entities, redact sensitive spans
•	UI: Streamlit app
Execution flow from code:
1.	run_pipeline.py
o	runs dataset generation if not skipped
o	runs training if not skipped
o	runs evaluation
o	optionally launches Streamlit
2.	data_generation/generate_dataset_from_reports.py
o	scans reports/
o	extracts text from each PDF
o	splits text into sentences
o	uses annotate_tokens_bio() to produce BIO tags
o	appends to train/dev/test files
3.	dataset/vocab_builder.py
o	builds vocabulary from training sentences
o	saves vocab.txt and tags.txt
4.	dataset/dataset_loader.py
o	loads CoNLL data
o	converts tokens to token IDs and tags to tag IDs
o	pads batches and returns DataLoader
5.	models/bilstm_crf_model.py
o	embedding -> BiLSTM -> dropout -> linear -> CRF
o	CRF does training loss and Viterbi decoding
6.	training/train.py
o	builds vocab
o	builds dataloaders
o	initializes model
o	trains over epochs with Adam + ReduceLROnPlateau + early stopping
o	saves best checkpoint
7.	training/evaluate.py
o	loads model
o	evaluates on test split
o	computes entity-level F1
8.	inference/predict.py
o	loads model and vocab
o	tokenizes text
o	predicts tags
o	reconstructs entity spans
9.	inference/redact_text.py
o	hybrid model + regex redaction
o	model-based redaction + regex fallback
10.	ui/streamlit_app.py
•	text mode and PDF mode
•	highlights detected entities
•	downloads results
Important architecture note:
•	There is no backend service, API gateway, or database.
•	Data is moved through files and Python objects only.
•	This is a training/inference pipeline, not a traditional web app.

6.	AI/ML pipeline and model details
The model is a BiLSTM + CRF sequence tagger.
From README.md and models/bilstm_crf_model.py:
•	Embedding layer
•	Bidirectional LSTM (2 layers)
•	Dropout
•	Linear projection
•	CRF on top
This is classic NER / sequence labeling:
•	token-level classification with BIO labels
•	model learns dependencies between labels through CRF transitions
•	used for clinical entity extraction

8.	Important algorithms and complexity
A. BIO sequence labeling
•	Tokens are labeled as B-ENTITY, I-ENTITY, or O
•	This lets model capture entity boundaries
B. CRF
•	Complexity per sequence roughly O(T * K^2)
o	T = sequence length
o	K = number of tags
•	Why used: it models transition structure between tags, which is crucial in NER
C. BiLSTM
•	Complexity O(T * H^2) for recurrent updates, with hidden state H
•	Why used: captures context left and right of each token
D. Entity-level F1 evaluation
•	utils/metrics.py computes strict span matching
•	set(_extract_entities(...)) ensures exact entity boundaries matter
•	This is better than token accuracy for NER

9.	Design decisions, alternatives, and trade-offs
Design decision 1: Hybrid model + regex Why:
•	model catches context-based NER
•	regex catches obvious formats like emails, phone numbers, IDs
•	hybrid improves recall
Trade-off:
•	regex may over-redact; model may miss rare entities
•	adds complexity and heuristic brittleness
Design decision 2: Local file-based dataset Why:
•	simple to run and debug
•	no external infra required
•	works for research/prototype
Trade-off:
•	poor scalability for large datasets or multi-user usage
•	not production-grade persistence
Design decision 3: BiLSTM + CRF Why:
•	strong on sequential text labeling tasks
•	not as heavy as transformer-based models for small corpora
•	easier to reason about in interviews
Trade-off:
•	less powerful than modern transformer NER models
•	limited context length compared to BERT-like encoders
Design decision 4: Streamlit UI Why:
•	fast to build
•	ideal for demoing ML workflows
•	no frontend engineering overhead
Trade-off:
•	not a robust app for real clinical deployment
•	poor scalability, no auth, no audit trail
10.	Bugs, weaknesses, limitations, and scalability
This is where the project is most interesting.
Weakness 1: No real database or safe storage
•	not production-safe for medical data
•	there is no schema, persistence abstraction, or access control
Weakness 2: Regex is handcrafted and brittle
•	utils/phi_extractor.py detects patterns with regex
•	edge cases:
o	names that do not match pattern
o	hospital names outside the template
o	multi-word locations not preceded by “in/at/from”
o	false positives in non-medical text
Weakness 3: Redaction reconstruction is lossy inference/redact_text.py:
Python
def _rejoin(original_tokens: List[str], new_tokens: List[str], original_text: str) -> str:
    result = original_text
    ...
    return " ".join(rebuilt)
This reconstructs by joining tokens with spaces. It does not preserve the original punctuation and whitespace layout. That means formatting can be changed, which is a real weakness in a document redaction system.
Weakness 4: Possible bug in checkpoint loading In training/evaluate.py:
Python
ckpt = torch.load(BEST_MODEL_PATH, map_location=device)
model.load_state_dict(ckpt["model"])
print(f"Loaded model from epoch {ckpt['epoch']} (best F1: {ckpt['best_f1']:.4f})")
But in training/train.py, the checkpoint is saved as:
Python
torch.save({
    "epoch": epoch,
    "f1": f1,
    "model": model.state_dict(),
    ...
}, BEST_MODEL_PATH)
The key is f1, not best_f1. So this looks like a real bug: ckpt['best_f1'] will fail with a KeyError if that code runs. This is a strong interview point.
Weakness 5: No training metadata or model card
•	no benchmark table
•	no evidence of real-world accuracy
•	no model drift monitoring
Scalability:
•	local training is okay for a prototype
•	not suitable for large-scale hospital pipelines
•	no async queue
•	no distributed workers
•	no server-timeouts or API load handling

13.	30-second, 1-minute, and detailed project explanation
30-second: “This project is a Python-based PHI de-identification pipeline for clinical reports. It extracts text from PDFs, labels sensitive entities like names, dates, phone numbers, and doctor names using a BiLSTM + CRF model, then redacts them before sharing data. It includes a Streamlit UI, real PDF processing, synthetic data generation, and evaluation using entity-level F1.”
1-minute: “This repo builds a local NLP pipeline for detecting and redacting PHI from clinical reports. It uses a BiLSTM + CRF model trained on BIO-tagged text, with regex rules as a fallback for common patterns like emails, phone numbers, and IDs. The workflow is: PDF or text input → text extraction → tokenization → BIO annotation → model training/inference → redaction → UI output. The model and data are handled through file-based artifacts in Python, and the project exposes a Streamlit demo app for text and PDF redaction. The main strengths are its sequence labeling architecture and hybrid model/regex design; the main weaknesses are lack of app security, no database, brittle regex logic, and a few likely code issues in the checkpoint/evaluation flow.”
Detailed:
•	The system’s actual value is in combining model-based entity detection with deterministic regex rules.
•	It is not a general-purpose clinical platform; it is a focused NLP redaction tool.
•	It demonstrates real sequence labeling design and practical redaction logic.
•	It is a solid interview project for ML/NLP engineering but not a production hospital system without major hardening.
